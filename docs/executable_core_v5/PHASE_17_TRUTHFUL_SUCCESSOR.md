## Fixed interpretation and the offered domain

The task catalog, interpreter, inherited protected observations, and meanings
are unchanged. A request supplies the actual finite source, one fixed context
and charge list, an ordered finite list of candidate/evidence offers, and a
search allowance. Neither caller-supplied success flags nor renamed tasks
replace recomputation of the existing obligations and semantic guard.

Exhausting that offered list proves that no offer in that list passes all
checks. For an admissible source and a complete task checker, it also proves
the absence of an accepted offer in that list. It does not prove that all production candidates or every constructible
successor have been enumerated. Exhausting the search allowance establishes
only the inspected prefix result. Search allowance is a count of offer checks;
it is not physical execution cost or a campaign resource authority.

## Formal interface

An offer contains the finite update, its proposed successor, and the original
finite evidence type. The total checker recomputes the eight `Facts` fields:
source and successor admissibility, typed successor equality, update validity,
trust bindings, resource validity, production/candidate matching, and strict
frontier expansion. It additionally checks failure of the offered task at the
actual source under the already fixed catalog.

For a complete task checker, success implies the existing guarded
`LearnedAcceptedStep`, semantic failure before and success after, protected-view
preservation, and exact finite recovery. The reverse equivalence and refusal
theorem require an admissible source. That condition is explicit because the
inherited accepted-step record does not independently assert source
admissibility. A failed check at an inadmissible source is therefore not
silently promoted to a theorem of nonexistence in that broader relation.

The generic ordered scan has three outcomes:

| Outcome | Established fact |
| --- | --- |
| Accepted offer at index `i` | The offered entry passes, `i` is within the inspection allowance, and every preceding offered entry fails. |
| Exhausted list | The entire supplied list was inspected and every entry fails. Under the admissible-source and complete-catalog hypotheses, no entry in that list is an accepted step. |
| Inspection-budget stop | The allowance is smaller than the list length and every inspected entry fails; uninspected entries retain unknown status. |

For an admissible source and a complete task checker, with enough allowance to
inspect the supplied list, an accepted result exists
if and only if an accepted offer is present in that exact list. An empty list
is exhausted even with zero allowance; a nonempty list with zero allowance
stops without inspecting an entry.

The catalog-bound theorem proves that the checked frontier has at most 282
tasks. Every linked sequence of checked strict steps satisfies
`initial_frontier_size + number_of_steps <= 282`. Consequently an unbounded
sequence of strict checked steps is impossible under these unchanged finite
meanings. This establishes a stopping boundary; it does not construct any
additional step or extend the improvement language.

## Runtime and concrete bridge

The Python interface fixes the exact preexisting AE interpretation bytes before
examining requests. It requires independently supplied source/request hashes,
bounded schemas, and an explicit ordered offer list. Verification recomputes
the complete result instead of trusting supplied outcome flags. The source
admissibility and finite-pool statements are separately reported.
Requests are detached from the caller, validated with exact schema types, and
converted to the canonical representation before their anchors are checked and
their offers inspected. Later caller mutations cannot retarget that inspection.
Canonical string normalization is therefore shared by hashing and evaluation.

The concrete bridge freshly reconstructs AF's retained inactive pair and
checks its exact packet, execution, and inherited implementation identities.
It then submits that same second-step offer to the new interface. Controlled
finite cases cover refusal, prefix search, exhaustion, budget stopping, and
substituted bindings. They are attributed as finite reference cases, not new
physical successors or live capability improvements.

Two explicit Lean counterexamples preserve the distinction: an exhausted empty
pool can coexist with a valid offer outside that pool, and an inspection-budget
stop can leave a valid offer in its uninspected suffix.

Python execution remains outside the general Lean refinement boundary. The
generic theorems concern the Lean definitions; the concrete generated cases
connect the selected serialized observations and reported outcomes to those
definitions. No general theorem equating arbitrary Python execution with Lean
execution is claimed.

## Validation and recovery contract

The gate retains AC's explicit completed-stage parent protocol. Eight modules
are freshly compiled, including the unchanged AF dependencies and the new
truthful-successor module; each receives a direct import-resolution check.
The positive certificate must emit the exact ordered named audit inventory.
Every negative control must establish its actual rejection lemma and fail only
at the designated final false assertion. Unrelated diagnostics, timeouts, and
unobserved native outcomes cannot count as intended rejections.

The source commit/tree, packet, generated proof bytes, pinned environment,
compiler outputs, compiled objects, and completed parent chain remain bound.
Saved-evidence reconstruction reopens that retained material without compiling
again. Historical proof campaigns, workers, and live challenges are not rerun.

The application kit is sealed before the actual Linux application. The Windows
handoff uses those same helper and payload bytes and records its own native
results. The previous AF workspace and evidence remain intact. Complete
execution recovery, including the objects omitted from Git, requires the source
and exact pinned environment; automatic relocation is not claimed.

## Claim boundary

The new completion flags are `truthful_successor_interface_checked` and
`finite_successor_stop_conditions_checked`. Only the complete actual pinned
Lean gate may set them true. All 24 broader claim flags remain false.

The inherited finite acceptance relation binds proposal keys and declared
prefix structure. It does not authenticate physical producer history or prove
every external controller/evaluator interface truthful. The selected AF bridge
retains AF's complete packet and package reconstruction; generic mathematical
offers are not presented as independently attested physical runs.
In particular, the inherited observation key is an input to the legacy task
meaning; the generic finite kernel does not prove that it is the cryptographic
hash of the supplied program descriptor. AF's selected byte bindings remain
separately checked.

The fixed catalog is finite. The bound on strictly expanding trajectories is
not an existence theorem for arbitrary future successors. Physical refinement,
full objective/evaluator integration, full resource authority, active promotion,
Gate E, Phase 17 exit, broad platform validation, and Phase 18 replay remain open.

The next integration obligation is to justify the offered candidate domain and
its connection to the actual producer/controller/evaluator at successive
sources. A truthful answer about an explicit offered pool cannot by itself
establish that an adequate successor was offered, that the pool covers a wider
production domain, or that future valid offers will continue to exist.
